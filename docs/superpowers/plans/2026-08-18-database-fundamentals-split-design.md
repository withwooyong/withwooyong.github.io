## 4. 축 정의 — 왜 이렇게 묶었나

원본이 이미 「개요 → 모델링 → SQL → 트랜잭션 → 종합」 순서를 갖고 있어 **축을 새로 만들지 않았다.**
각 편이 답하는 질문으로 축을 확인한다.

| 편 | 이 편이 답하는 질문 | 단독 가독 (`CR-4.4`) |
| :---: | --- | --- |
| 1 | 어떤 DB를 왜 고르는가 | 용어 정의를 이 편이 갖는다. 뒤 편들이 참조한다 |
| 2 | 데이터를 어떤 구조로 담는가 | 정규화 용어는 이 편에서 정의 |
| 3 | 같은 데이터에서 왜 어떤 SQL은 느린가 | 인덱스·실행계획 용어를 이 편이 정의. §2의 「선행 `%` LIKE」는 편1 링크 |
| 4 | 여러 요청이 같은 행을 건드리면 무슨 일이 나는가 | 락·격리수준을 이 편이 정의 |
| 5 | 위 넷을 실제 선택·장애 상황에 어떻게 적용하는가 | 앞 4편으로 링크 |

### 4-1. ⚠️ 편1이 지도편과 개요를 겸한다

앞 배치는 편1이 §0~§4 다섯 절을 받아 **내용 편이면서 지도편**이었다(`role: "map"`).
이번도 같다 — §0(용어)·§1(한눈에)·§2(DBMS 개요)가 시리즈 도입부 역할을 그대로 한다.

⇒ 편1에 `role: "map"`을 부여한다. 앞 배치에서 **inbound 1이라 지도편 게이트에 안 걸린 사고**
(인수인계 §7)가 있었으므로, 이번에는 처음부터 명시한다.

**지도편은 「완성해서 커밋」할 수 없다** — `CR-4.3`은 전체 목차를 요구하고 링크 검사는 대상 실재를
요구한다. 앞 배치가 이 충돌에 막혔다. 목차 링크를 **한 줄씩 나중에** 채운다.
