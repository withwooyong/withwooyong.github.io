# 발행 체크리스트

> 이 문서는 **기계가 판정할 수 없는 규칙만** 담는다.
> 스키마·금칙어·링크·분량·산출물은 게이트가 본다 — 여기 옮겨 적지 마라.
> 규칙을 문서에 복사하면 갈라진다(금지선 54).

전수 분류 근거는 `docs/superpowers/reports/2026-08-18-rule-triage.md`.
사장 판정된 규칙은 각 설계서 §11에 **취소선으로 남아 있다** — 번호로 참조되므로 지우지 않았다.

## 0. 게이트가 이미 보는 것 — 여기 없는 이유

**아래 항목이 이 체크리스트에 없는 것은 빠뜨린 것이 아니라 기계가 보기 때문이다.**

| 무엇 | 정본 |
| --- | --- |
| 프론트매터 필수 필드 · 카테고리 실재 · 태그 통제 어휘 · `series`/`seriesOrder` · 슬러그 · 스키마 밖 키 | `tests/blog/frontmatter.test.ts` |
| 금칙어 HARD/SOFT · 표기 체계별 단어 경계 · 적용 범위 | `scripts/check-forbidden.mjs` |
| 축자 복제 | `scripts/dup-scan.mjs` |
| 정적 export · `trailingSlash` · `fs` 위치 · 타입 | `npm run build` · `npx tsc --noEmit` |
| 발행본 전수 스키마 · **분량 하한** | `tests/blog/content/schema.test.ts` |
| 내부 링크 실재 · 슬래시 종결 · inbound 0 고립 · **카테고리 고립** | `tests/blog/content/links.test.ts` |
| 기존 페이지 산출물 불변 | `scripts/check-baseline.mjs` (로컬 전용 — CI에는 `out/`이 없다) |
| 발행본 수 · 카테고리별 분포 | `scripts/check-counts.mjs` |

### 자동으로 분류됐으나 검사기가 아직 없는 것 — 당분간 사람이 본다

아래 3건은 **기계가 판정할 수 있다고 판정됐다.** 검사기가 생기면 이 문서에서 뺀다.
그때까지 지우면 아무도 안 보므로 남겨 둔다.

| 규칙 | 어떤 검사로 잡히나 | 현재 위치 |
| --- | --- | --- |
| 금지선 26 | `grep -rn "^#\{1,3\} .*첫 90일" content/blog` | §7 |
| `CR-1.2` | 본문 앞부분에서 `> **작성 기준일**` 계열 리터럴 | §7 |
| `CR-2.3` | `*qna*` 슬러그 → `^## Q. ` 블록마다 표·코드·도식 | §7 Q&A |

⚠️ **「0건」을 믿기 전에 검사기가 무엇을 잡는지 증명하라.** 순서가 규칙이다 — `:verify` 먼저, 스캔 나중.
증명 없는 0건은 거짓 음성과 구분되지 않는다(금지선 53).

## 1. 귀속 — 이 판정은 누구의 것인가

| ✔ | 확인 | 실패 사례 |
| :---: | --- | --- |
| ☐ | 새로 만든 판정·분류·대조에 **「이 글의 정리다」 귀속을 붙였다** | 붙일 수 없는 판정이면 쓰면 안 되는 판정이다 (금지선 14) |
| ☐ | 그 판정이 **정말 이 글이 만든 것인지 원본에서 확인**했다 | 원본 `09:41` 축자였던 「그 이상」에 귀속을 붙여 **강등**할 뻔했다 (금지선 32) |
| ☐ | 「원 자료는 X를 하지 않았다」를 썼다면 **X가 있을 만한 자리를 검색하고 그 근거를 문안에 남겼다** | 귀속은 이 형태를 방어하지 못한다 (금지선 15) |
| ☐ | 인용한 좌표가 **「무엇의 무엇」인지** 한 줄로 적을 수 있다 | 편9 `:17`은 「순서를 지켜라」가 아니라 **「원 자료의 서술 순서 그대로다」**였다 (금지선 35) |
| ☐ | 표의 「근거」 열이 **그 원본 파일 안에서** 실재한다 | 합계 검산도 행간 대조도 「근거가 파일 밖을 가리키는」 형태를 못 잡는다 (금지선 18) |
| ☐ | 원본이 밝힌 **자기 출처를 검증 없이 믿지 않았다** | 「이 문서는 A~I를 취합했다」는 원본의 주장이지 실측이 아니다 (금지선 19) |

## 2. 전수 배정 — 전칭을 쓰기 전에

| ✔ | 확인 | 실패 사례 |
| :---: | --- | --- |
| ☐ | 전칭(「전부」)을 분류로 바꿀 때 **항목을 전수 배정하고 셌다** | 「전부」는 반례 하나로, 「N갈래」는 미배정 하나로 무너진다 (금지선 16) |
| ☐ | 전수 배정을 마친 뒤 **그것을 요약하는 총평 문장을 붙이지 않았다** | 배정이 정확해도 그 아래 한 줄에서 새 전칭이 생긴다 (금지선 17) |
| ☐ | 「**N개는 전부 X다**」 꼴을 만나면 **고치지 말고 삭제했다** | 편2 `:450`이 3회 왕복했다. N을 고치면 X가 안 맞고 X를 고치면 N이 안 맞는다 (금지선 29) |
| ☐ | 같은 대상을 두 자리에서 쟀다면 **술어의 넓이를 맞췄다** | 「글자까지 똑같이」 2편으로 잰 값을 「작업 틀로 정의한다」(=3편)에 옮겼다 (금지선 36) |
| ☐ | 표를 **가로로** 읽었다 | 같은 행의 3열과 4열이 서로를 반박하고 있었다. 세로로 읽으면 절대 안 보인다 (금지선 37) |
| ☐ | 표를 요약한 문단이 **배타 전칭**을 만들지 않았다 | 표 4행은 안전했고 그것을 가로로 요약한 2문단에서 다섯 번 연속 결함이 났다 (금지선 38) |

⚠️ **검사기로 만들지 않기로 한 축이다.** 「전부」 단독 310건 대 「숫자+전부」 14건이고,
기계는 N이 맞는지만 알 뿐 **술어 X가 맞는지 판정하지 못한다.**
못 하는 일을 하는 척하는 검사기가 가장 위험하다(설계서 §3-4).

## 3. 삭제 파급 — 지우기도 안전하지 않다

| ✔ | 확인 | 실패 사례 |
| :---: | --- | --- |
| ☐ | 지우기 전에 **같은 주장의 다른 사본**을 핵심어로 전수 grep했다 | 판정표가 `:90` 한 좌표만 지목해 `:76`·`:82`가 남았다 (금지선 31 ①) |
| ☐ | 지우기 전에 **그 문장이 떠받치던 근거**를 앞뒤를 읽어 확인했다 | 앞부분을 지우자 남은 문장이 **발행본에 없는 제목**을 가리키게 됐다 (금지선 31 ②) |
| ☐ | 지우기 전에 **다른 자리가 그것을 참조하는지** 실측했다 | `source`를 걷자 `CR-1.10`의 뒷받침이 사라졌다. 규칙은 유효한데 근거가 없어졌다 (금지선 55) |
| ☐ | 도식 노드를 지울 때 **그 노드가 다른 절의 전제인지** 먼저 확인했다 | `approval rules`를 걷으면 「본문에서 실제로 쓰이는 것만 모았다」는 `:22`의 선언이 거짓이 된다 |
| ☐ | 표에서 낱말 하나를 바꿀 때 **그 낱말에서 파생된 칸**을 함께 셌다 | 한 금칙어를 치환하려는데 초성·자소·영타·한타 **네 칸이 그 낱말의 파생값**이었다. 자판 매핑 한 글자가 틀리면 기술 문서가 거짓이 된다 (금지선 57) |

> **지우기가 안전한 것은 「그 자리」에서다.** 결함이 같은 자리에서 세 번 이상 나면
> 고치기보다 **그 자리의 존재를 의심하라** (금지선 38).

## 4. 익명화 — 지운 자리를 메우지 마라

| ✔ | 확인 | 실패 사례 |
| :---: | --- | --- |
| ☐ | 금칙어를 걷기 전에 **그 낱말이 지고 있던 정보**를 적었다 — 조건인지, 출처인지, 화법인지 | 조건·출처는 남기고 **화법만** 걷는다 (`CR-1.9`) |
| ☐ | 주체를 **갈아 끼우지** 않았다 | 없는 주체를 세우면 원본이 하지 않은 검증 불가능한 주장이 생긴다 (`CR-1.10`) |
| ☐ | 지운 자리를 일반화로 **메우지** 않았다 | **새로 쓴 문장은 예외 없이 지적을 받았다. 타율 100%다** (금지선 44) |
| ☐ | 열을 지웠다면 **열을 지우는 것으로 끝냈다** | 「나의 현재 위치」 열의 빈 칸을 메우려다 원문에 없는 주장이 생겼다 (금지선 21) |
| ☐ | 오탐이라도 **의미 손실 없이 치환 가능하면 치환**했다 | 「신규 **입사**자」를 오탐으로 두려 했으나 원본 자신이 같은 행에서 「신규 합류자」를 쓰고 있었다 (금지선 34) |
| ☐ | 회사 내부 수치·조직 구조·미공개 일정을 일반화했다 | 사명은 **익명화**(「OTT 서비스」·「IPTV 서비스」)하되 **제품명은 유지**한다 (`CR-3.4`) |

> **리뷰 대안 중 「삭제」와 「최소 치환」을 우선 채택하라.** 실제로 이 원칙을 적용하자 새 지적이 나오지 않았다.

## 5. 도식 근거 — 노드도 화살표도

| ✔ | 확인 | 실패 사례 |
| :---: | --- | --- |
| ☐ | 새로 그린 mermaid의 **모든 화살표**에 본문 근거 줄이 있다. 근거표를 함께 제출했다 | (금지선 28) |
| ☐ | **노드 라벨**에도 본문 근거가 있다 | 앞 배치의 무근거는 전부 화살표였으나 다음 배치는 **노드**였다 — 고유명 4개가 본문 근거 0줄로 실렸다 (금지선 30) |
| ☐ | 분할 후 **도식과 그 설명이 같은 편에** 있다 | 문서당 도식이 11~25개라 절 경계를 잘못 잡으면 갈라진다 (`CR-4.5`) |
| ☐ | 원본 절별 도식 수와 발행본 편별 도식 수를 **대조**했다 | 총합만 비교하면 **이동과 유실을 구분할 수 없다** (`CR-6.2`) |
| ☐ | 「중복이다」라는 **인상으로** 도식·표를 지우지 않았다. 항목 수를 셌다 | 세어 보고 브리프를 어겨도 된다. **어긴 이유를 보고하라** (금지선 1 · `CR-1.6` · `CR-6.1` · `CR-6.3`) |

## 6. 링크가 약속한 것 — 검사기가 못 보는 층

⚠️ **링크 검사기 통과는 이 항목의 통과가 아니다.**
검사기는 「슬러그가 실재하는가」를 본다. 아래는 「그 편이 약속한 것을 주는가」다.

| ✔ | 확인 | 실패 사례 |
| :---: | --- | --- |
| ☐ | 「거기서 무엇을 다룬다」를 썼다면 **대상 파일을 열어 `파일:줄`로 확인**했다 | 「분석기가 BM25 **점수에** 어떻게 개입하는지는 …에서 다룬다」 — 대상 편 251줄에 **잇는 서술 0건**. 링크는 살아 있었다 (금지선 45) |
| ☐ | 링크가 **출발 편이 스스로 세운 축**을 어기지 않았다 | 출발 편이 recall 축과 순위 축을 갈라 놨는데 recall 내용을 **순위 축**에 붙였다 |
| ☐ | 리포 자신의 **라우팅과 충돌하지 않는다** | 다른 편이 그 질문의 행선지를 **제3의 편**으로 안내하고 있었다 |
| ☐ | 낱말이 같아도 **물건이 같은지** 확인했다 | 「리랭커」가 한쪽은 **LTR**, 다른 쪽은 **Cross-Encoder**였다. grep으로는 완벽한 후보였다 (금지선 47) |

## 7. 톤 · 도입부 · 단독 가독

| ✔ | 확인 | 근거 |
| :---: | --- | --- |
| ☐ | 1인칭 학습 기록 톤을 **설명체로 전환**했다 — 「~를 학습했다」 → 「~는 ~하게 동작한다」 | `CR-1.1` |
| ☐ | 원본 메타 인용문(`> 작성 기준일 / 목적 / 원본`)을 **본문에서 제거**했다 | `CR-1.2` — **자동 · 미구현.** 검사기 생기면 뺀다 |
| ☐ | 「본인 실적이 아니다」류 **방어적 주의문을 제거**했다 | `CR-1.3` |
| ☐ | **도입부를 새로 썼다** — 어떤 문제를 다루고 누가 읽으면 좋은지 2~3문장 | `CR-1.5` |
| ☐ | 분할 후 **각 글이 단독으로 읽힌다.** 앞 글에만 있는 용어는 재정의하거나 링크했다 | `CR-4.4` |
| ☐ | 분할이 **H2 경계**를 지켰다. 문단 중간을 자르지 않았다 | `CR-4.1` |
| ☐ | **절 하나가 상한을 넘으면 H3 경계로 내려갔다** — 상한 수치는 `CR-4.1a`가 정본이다 | ⚠️ **검사기가 이것을 보지 않는다.** `schema.test.ts` 는 **하한만** 본다(`:15` 「상한은 검사하지 않는다 — 금지선 13」). 아래 금지선 13과 **다른 것을 잰다** — 13은 「줄이지 마라」, 이것은 「어디서 자르나」다 |
| ☐ | 시리즈 첫 글에 **전체 목차와 각 편 요약**이 있다 | `CR-4.3` |
| ☐ | **상한을 이유로 내용을 빼지 않았다** — 상한은 합격선이 아니다 | 상한을 맞추려 축약 용어표 행을 삭제한 사고가 있었다 (금지선 13) |
| ☐ | 「첫 90일에 할 일」을 **편 제목·H2로 쓰지 않았다** | 발행본 **9편**이 마무리 표의 **열 제목**으로 쓰고 있다 (금지선 26 — 원문의 「7편·마무리 절」을 실측으로 정정). **자동 · 미구현** — `grep -rn "^#\{1,3\} .*첫 90일"` 이 곧 검사기다 |

### Q&A 편

| ✔ | 확인 | 근거 |
| :---: | --- | --- |
| ☐ | 질문이 **기술 질문 형태**다. 「면접에서 자주 나오는」 같은 수식이 없다 | `CR-2.1` |
| ☐ | 답변이 **결론 먼저, 근거 다음** 순서다 | `CR-2.2` |
| ☐ | 답변마다 표·코드·도식 중 **하나 이상**이 있다 | `CR-2.3` — **자동 · 미구현.** `*qna*` 슬러그로 대상을, `^## Q. ` 로 블록을 잡는다 |
| ☐ | 개인 경력 서사를 제거하거나 회사명 없이 일반화했다 | `CR-2.4` |
| ☐ | 분량 상한을 넘으면 **주제별로 분할**했다 — **임계값은 `CR-2.5`가 정본이다. 여기 복사하지 마라** | `CR-2.5` (§14-1에서 편수 기준 → 분량 기준으로 정정) |

## 8. 프로세스 — 브리프와 리뷰를 짤 때

발행물 자체가 아니라 **작업을 설계할 때** 보는 항목이다.

| ✔ | 확인 | 실패 사례 |
| :---: | --- | --- |
| ☐ | **검증자·리뷰어의 처방 문안을 그대로 붙여넣지 않았다.** 채택 전 3검사: ① 기발행 전편 grep ② 원본 근거 확인 ③ 전제절·단서 소실 여부 | 처방도 검증 대상이다 (금지선 20) |
| ☐ | 두 대안을 동시에 채택할 때 **두 자리의 물리적 거리**를 확인했다 | `:32`와 `:34`가 두 칸 거리라 각각 옳은 대안이 문면을 공유하게 됐다 (금지선 46) |
| ☐ | 리뷰어에게 **앞선 지적 목록을 주지 않은 새 눈**을 최소 1기 넣었다 | 목록을 받은 2판은 1건, 목록 없는 `fresh`는 **6건**을 냈다 (금지선 48) |
| ☐ | **독자 축**을 넣고 **좌표를 주지 않았다.** 「다른 파일을 열어 사실 확인을 하지 마라」를 브리프에 명시했다 | 좌표를 주면 N+1번째 좌표 대조가 된다. 정확성 검증이 강할수록 글에 자기 감사가 쌓인다 (금지선 43) |
| ☐ | 브리프의 「미확정」이 **정말 아직 아무도 안 내린 판정인지** 확인했다 | 편1이 이미 해소한 갈림을 「미확정」으로 열어 뒀다 (금지선 42) |
| ☐ | 검증자 진단이 「A가 없다」면 **A 전체**를 쟀다. 좁은 확인으로 통과시키지 않았다 | 「종료조건이 아니라」만 grep했다. 「사람 게이트」 전체를 grep했으면 두 건이 나왔다 |
| ☐ | 개념 검색을 **직설어·완곡어·반의어 3계열**로 나눠 돌렸다 | 유효성 대조까지 마친 「0건」이 거짓이었다 — 「**격하**」·「**규모로 분기**」라는 어휘로 이미 발행돼 있었다 (금지선 33) |
| ☐ | 「0건」을 문서에 적기 전에 **검사기가 무엇을 잡는지 증명**했다 | 거짓 음성은 「못 찾음」이 아니라 「**없음을 확인함**」으로 기록된다 (금지선 53) |
| ☐ | 앞 배치에서 규칙이 작동한 **사례를 표로** 브리프에 넣었다 | 규칙만 적으면 따르지 않고, 사례를 보면 센다 (`CR-6.4`) |

### 8-a. 배치를 마감할 때 — 순서가 규칙이다

편별 커밋이 끝났다고 배치가 끝난 것이 아니다. 아래 다섯을 **이 순서로** 돌린다.
`:verify` 가 앞서는 이유는 §0 말미와 같다 — 증명 없는 0건은 거짓 음성과 구분되지 않는다.

| # | 명령 | 무엇을 보나 | 왜 이 자리인가 |
| ---: | --- | --- | --- |
| 1 | `npm run build` | 정적 export · sitemap 갱신 | 2번이 산출물을 읽는다 |
| 2 | `npm run check-forbidden:built` | **산출물**의 HARD 0 | 소스가 깨끗해도 템플릿이 `og:image`·제목을 주입한다. 빌드 없이 돌리면 종료코드 **2**로 「`out/blog` 없음」을 알린다 — 거짓 0이 아니라 |
| 3 | `npm run check-baseline` | 비블로그 페이지 산출물 불변 | **로컬 전용.** CI에는 `out/` 이 없다 |
| 4 | `npm run check-counts:verify` | 검사기가 실제로 잡는지 | 증명 먼저 |
| 5 | `npm run check-counts` | 문서에 적힌 편수가 실제와 일치 | 갱신을 잊으면 여기서 막힌다 |

5번이 **마감을 강제하는 장치**다. 손으로 고치는 절차는 잊히고, 실제로 3배치가
CHANGELOG에서 통째로 빠진 적이 있다. 어느 문서의 몇 곳을 보는지는
`scripts/check-counts.mjs` 가 정본이다 — **이 문서에 옮겨 적지 마라.** 옮겨 적은 목록이
낡는 것이 금칙어 거짓 0을 만든 바로 그 구조다.

마감 커밋을 나누는 기준:

| 무엇 | 커밋 종류 | 왜 |
| --- | --- | --- |
| 새 편이 기존 편에서 받는 **inbound 링크** | **`feat(blog):`** | 발행본 본문이 바뀐다. `docs:` 로 묶으면 pre-commit 훅이 도는 커밋과 안 도는 커밋이 한 덩어리가 된다 |
| CHANGELOG · README 수치 | `docs:` | |
| 인수인계 · 설계서 마감 기록 | `docs:` | |

## 9. 배치 지시는 여기 넣지 마라

> **배치 스코프 지시(「이번 범위가 아니다」·「이 파일의 이 절만」)는 그 배치의 설계서에만 적는다.**
> 이 체크리스트·`GC-*`·`CR-*`에 넣지 않는다.
> 영구 규칙은 **「어느 배치에서도 참인가」**를 통과해야 한다.

2026-08-18 전수 분류에서 **금지선 14개가 이 원칙 위반으로 사장 판정**됐다.
전부 그 배치가 끝난 뒤에도 목록에 남아 매 세션 읽히고 있었다
(예: 금지선 8이 「손대지 마라」고 한 파일을 커밋 `6a56f4a`가 이미 발행했다).
