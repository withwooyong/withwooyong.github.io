<a id="t1"></a>
### 1. 파이프 뒤 종료 코드

`$?` 는 **마지막** 명령의 것이다. `grep … | sort | uniq -c` 는 grep이 0건이어도 항상 0으로 끝난다.

**대응** — 종료 코드를 읽을 작정인 명령은 파이프 없이 단독으로 실행한다.

<a id="t2"></a>
### 2. 한글 1인칭

grep이 양방향으로 실패한다.

| 방향 | 예 |
| --- | --- |
| 오탐 | 「동시성 문**제가**」 · 「메이**저는**」 |
| 누락 | 「**내** 검색 커리어」 |
| 넓히면 홍수 | `내 [가-힣]{2,6}` → 「인덱스 **내** 문서」가 쏟아진다 |

**대응** — 매칭된 줄을 열어 읽는다. **1인칭은 검사기에 넣지 마라.** 자동화가 불가능한 항목이다.

<a id="t3"></a>
### 3. 한글 종결어미는 줄 끝에 오지 않는다

「…있습니다.」는 마침표로 끝나므로 `습니다$` 는 **아무것도** 맞히지 못하고 구조적 0을 보고한다.
브리프에 「~로 끝나는 줄」이라고 쓰면 에이전트가 정확히 그 앵커 패턴을 짠다.

**대응** — 앵커가 아니라 **부분 문자열**로 센다. 줄이 아니라 출현 횟수를 센다 (한 줄에 둘이 올 수 있다).
그다음 0이 아님이 확실한 절과 대조한다.

<a id="t4"></a>
### 4. 마크다운 강조가 단어를 쪼갠다

`**IDOL**을` 은 `IDOL을` 에 걸리지 않는다. 한글은 조사가 바로 붙으므로 구조적으로 발생한다 —
영어는 띄어쓰기가 있어서 같은 문제가 생기지 않는다.

**대응** — 강조를 벗긴 패턴도 같이 검색한다.

<a id="t5"></a>
### 5. 로케일이 한글과 이모지를 가린다

`LC_ALL=C` 없이는 이모지 grep이 거짓 0을 낸다. 그렇다고 `LC_ALL=C grep -P '[\x{1F300}-\x{1FAFF}]'`
를 쓰면 `range out of order` 로 죽는데, **출력이 없는 것은 발견이 없는 것과 똑같이 보인다.**

**대응** — `LC_ALL=C` 를 고정하고 이모지는 UTF-8 바이트 패턴으로 매칭한다.
`|| echo "0건"` 을 절대 붙이지 마라 — 「파일 없음」과 「0건」이 같은 문자열이 된다.

<a id="t6"></a>
### 6. 단어 안의 부분 문자열

`grep -o '비용'` 이 「대**비용**(對比用)」도 센다.

**대응** — 히트한 줄을 열어 의도한 단어인지 확인한다.

<a id="t7"></a>
### 7. 축자 중복 검사의 맹점

`scripts/dup-scan.mjs` 는 문자열만 본다. "같은 뜻, 다른 표현"은 보지 못한다.

**대응** — 문자열뿐 아니라 뜻으로도 정의를 대조한다. 검사기의 0은 축자 중복이 없다는 뜻일 뿐이다.

<a id="t8"></a>
### 8. 히어독이 백슬래시 한 겹을 먹는다

따옴표를 씌운 `<<'EOF'` 에서도 정규식의 `\\` 가 `\` 로 도착해 `SyntaxError` 를 낸다.
홑겹은 살아남고 겹겹만 벗겨진다. 히어독 안의 셸 따옴표가 히어독 자체를 깨뜨릴 수도 있다.

**2026-08-27 재확인** — `node -e '…[^\\]…'` 를 Bash 도구로 넘겼더니 `[^\]` 로 도착해
`Unterminated regexp literal` 로 죽었다. 이 문서를 만드는 작업 중에 다시 걸렸다.

**대응** — 그런 파일은 `Write`/`Edit` 도구로 쓰거나 `String.fromCharCode(92)` 로 문자를 만든다.
검증 스크립트처럼 정규식이 든 것은 파일로 써서 실행하는 편이 확실하다.

<a id="t9"></a>
### 9. grep은 CRLF를 감지하지 못한다

CR을 줄 끝으로 처리하므로, CR이 **393개**인 파일을 "LF 전용"으로 보고했다.

**대응** — `tr -cd '\r' | wc -c` 로 바이트를 센다.

<a id="t10"></a>
### 10. `core.autocrlf=true` 가 줄바꿈 변경을 숨긴다

git이 정규화한 뒤 비교하므로, 통째로 다시 쓴 파일도 깨끗한 diff로 보인다.
이 리포는 실제로 CRLF와 LF가 섞여 있다.

**대응** — 깨끗한 diff는 아무것도 바뀌지 않았다는 증거가 **아니다.**
대조 파일을 두고 CR/LF를 직접 센다.

<a id="t11"></a>
### 11. 서브에이전트가 보고 없이 유휴 상태가 된다

`reviewer` 와 `scout` 에는 `Write` 도구가 없다. `scout` 과 `verifier` 가 통지 3번에 걸쳐
아무것도 내놓지 않은 적이 있다.

**대응** — 메시지가 아니라 파일로 판단한다. 유휴 통지마다 `ls -la <스크래치패드>` 를 돌리고,
그다음 `SendMessage` 로 보고서를 회수한다. 이때 **원래 질문을 그대로** 다시 보낸다 —
「아까 물어본 대로」라고 하면 껄끄러운 항목부터 떨어져 나간다.

<a id="t12"></a>
### 12. `grep -r` 이 `out/` 과 `node_modules` 를 훑는다

120초 타임아웃.

**대응** — `Grep` 도구를 쓰거나 `--include` / 명시적 경로를 준다.

<a id="t13"></a>
### 13. Tailwind가 주석까지 훑는다

클래스 추출기가 원본 텍스트에 대한 정규식이라 주석을 파싱해 걸러내지 않는다.
**주석 안**에 쓴 임의값 클래스가 진짜 CSS로 방출된다.

주석에 예시로 남긴 `bg-[url('./${logo}')]` 가 규칙이 되어 PostCSS가 해석을 시도했고,
빌드는 **아무도 import하지 않은 파일 이름**을 가리키는 `Cannot find module './${logo}'` 로 죽었다.
(사이트 리뉴얼 T1에서 실제로 발생)

**대응** — 주석에 대괄호 임의값 클래스를 절대 넣지 마라. 예시는 산문으로 쓰거나 필드 이름만 적는다.

<a id="t14"></a>
### 14. Git Bash의 `sed -i` 가 CR을 전부 지운다

파일을 LF로 다시 쓴다. CRLF 파일이면 CR **531개**가 조용히 사라지는데,
`core.autocrlf=true` 가 정규화하므로 `git diff` 는 여전히 한 줄짜리 깨끗한 변경으로 보인다.
**git 기반 검사 전부에 이 손상이 보이지 않는다.** (사이트 리뉴얼 T4에서 실제로 발생)

**대응** — CRLF 파일에 `sed -i` 금지. `Edit` 도구(부분 치환이라 주변 CR이 보존된다)나 Node로 읽고 쓴다.
**`Write` 는 대안이 아니다 — [16번](#t16) 참조.**
검증은 바이트 수(`tr -cd '\r' | wc -c`)로 한다. `git diff` 나 `cat -A` 로 하지 마라 —
MSYS의 `sed | cat -A` 도 CR을 지워서 어느 쪽이든 LF 전용으로 보고한다.

<a id="t15"></a>
### 15. Tailwind variant 클래스는 빌드된 CSS에 백슬래시를 문자로 갖는다

`.focus-visible\:ring-signal{…}` 에서 `\` 는 이스케이프가 아니라 셀렉터 텍스트의 일부다.
잘못 이스케이프한 패턴으로 grep하면 **0과 종료 코드 1** 이 나오는데,
이는 "Tailwind가 그 클래스를 방출한 적 없다"와 똑같이 읽힌다.

**실측 (같은 파일)**

| 명령 | 결과 |
| --- | --- |
| `grep -c 'focus-visible\\:ring-signal'` | 0 |
| `grep -cF 'focus-visible\:ring-signal'` | 1 |

태스크 브리프가 구현자에게 이중 백슬래시 형태를 그대로 건네준 것이 발단이었다.

**대응** — 빌드된 CSS 셀렉터는 `-F` 와 홑 백슬래시로 grep한다.
증명하지 않은 0으로 "클래스가 방출되지 않았다"를 결론짓지 마라 — 존재가 확실한 클래스를
대조군으로 먼저 검색한다.

<a id="t16"></a>
### 16. `Write` 도구가 전체 교체 시 CRLF를 떨어뜨린다

받은 문자열을 그대로 쓰는데 그 문자열에 CR을 넣을 실질적 방법이 없어서,
전체 파일 쓰기는 항상 LF로 떨어진다.

**실측 (3줄 CRLF 표본)**

| 도구 | CR | LF |
| --- | --- | --- |
| `Edit` | 3 | 3 |
| `Write` | **0** | 3 |

이것이 나쁜 이유는 [14번](#t14)이 `sed -i` 의 대안으로 `Write` 를 지목했었기 때문이다 —
**권장 해법의 절반이 같은 결함을 갖고 있었다.** T6 수정 라운드에서 `components/theme-toggle.tsx`
의 CR 52개가 0이 되며 실제로 터졌다.

**대응** — 먼저 파일의 줄바꿈을 확인한다(`tr -cd '\r' | wc -c`).
LF 파일이면 `Write` 무방. CRLF면 `Edit`, 전체를 바꿔야 하면 Node로.
그리고 항상 CR을 다시 센다 — `git diff` 는 이것을 보여주지 못한다.

<a id="t17"></a>
### 17. `next/head` 가 하이드레이션 때 head 태그를 다시 넣는다

`out/blog/index.html` 에서 `<link rel="canonical">` 을 통째로 지워도 E2E 검사는 **초록**이었다.
Next의 head 매니저가 하이드레이션에서 되돌려 놓고, 로케이터는 복원된 DOM만 본다.

태그는 배포되는 바이트에 실제로 없었고, 그것이 Slack·카카오톡 언펄과 대부분의 크롤러가 읽는 것이다.
`check-forbidden:built` 와 같은 모양이다 — 깨끗한 소스 ≠ 깨끗한 산출물,
여기서는 깨끗한 *DOM* ≠ 깨끗한 산출물. (T8에서 실제로 발생)

**대응** — **원본 응답**에 대해 단언한다: `page.request.get(path)` + 텍스트 정규식.
DOM도 보되 두 번째의 **별개** 측정으로 본다. 헬퍼는 `e2e/raw-html.ts` 에 있다.

<a id="t18"></a>
### 18. React가 `#__next` 안에 손으로 넣은 마크업을 버린다

셀렉터를 시험하려고 `out/index.html` 의 `#__next` 아래에 탐침 `<div>` 를 넣었더니 **0건**이 나왔다.
하이드레이션이 트리를 조정하며 떨궜다. 검사기는 멀쩡한데 **실험 쪽이 "검사기가 고장났다"로 읽힌다.**
(T8에서 E2E 셸 게이트를 증명하다가 발생)

**대응** — React의 영역 밖을 건드린다: `<body>` 의 속성이나 `<head>` 노드.
`<body data-site-shell>` 로 같은 탐침을 다시 돌리니 설계대로 게이트가 뒤집혔다.

<a id="t19"></a>
### 19. Playwright의 종료 코드는 양방향으로 거짓말한다

| 상황 | 종료 코드 | 왜 헷갈리나 |
| --- | --- | --- |
| `-g` 가 아무것도 못 맞힘 | **1** + `No tests found` | 진짜 실패와 구분되지 않는다 (실제 사례: 어떤 제목에도 없던 `-g "다크 기본"`) |
| `retries: 1` 로 두 번째에 통과 | **0** + `1 flaky` | 실측: 같은 스펙에서 `CI` 미설정 → 1, `CI=true` → 0 |

별개로 `list` 리포터는 `test.skip` 사유를 찍지 않아서, 게이트된 스위트가 설명 없는 침묵으로 보인다.

**대응** — `$?` 만이 아니라 요약 줄을 읽는다. `retries: 0` 을 유지한다 (이유는 `playwright.config.ts` 에 있다).
게이트 상태를 `describe` 제목에 넣어 skip이 스스로 설명하게 한다.

<a id="t20"></a>
### 20. `-g` 필터가 스위트의 skip을 정당화하던 센티넬을 없앤다

이 리포는 게이트된 스위트마다 **별도** `describe` 에 센티넬을 짝지어 둔다.
그래서 게이트된 테스트를 고를 만큼 좁은 필터는 센티넬도 같이 떨군다.

**실측 2026-08-27**

```
npx playwright test e2e/search.spec.ts -g "검색 팔레트" --project=desktop
  -> 4 skipped, 종료 코드 0
```

완벽한 조용한 초록이다 — 의미 있는 것이 전부 skip되고,
그것을 말해 줄 유일한 테스트가 필터로 빠졌기 때문에 성공을 보고한다.

**대응** — 필터를 건 실행의 초록을 통과로 취급하지 마라.
게이트 상태는 **전체** 실행으로 판단하고, `$?` 가 아니라 skip 수를 읽는다.
센티넬과 그 게이트는 한 몸이고 필터는 그것을 가른다.

<a id="t21"></a>
### 21. `npm ci --dry-run` 이 실제로 `node_modules` 를 지운다

시뮬레이션이 아니다. npm은 멈출지 결정하기 **전에** 트리를 지우므로,
"드라이런"이 설치 패키지 **0개**를 남긴다 (실측 590 → 0).

이후 모든 도구가 npm이 아니라 자기 이야기를 하며 실패한다.
그 시점에 `npm test` 를 읽은 병렬 에이전트가 `'vitest' is not recognized` 를 받고
**"vitest가 설치되지 않았다"고 보고했다.** 리눅스 전용 의존성이 CI에서 설치될지 확인하려다 발생.

**대응** — 무엇이 설치될지 보려고 `npm ci --dry-run` 을 쓰지 마라.
대신 `package-lock.json` 을 읽는다 (`os`/`cpu`/`optional` 필드에 플랫폼 정보가 있다).
이미 돌렸다면 `npm ci` 로 복구하고, 이후의 어떤 실패든 믿기 전에 `ls node_modules | wc -l` 로 확인한다.

### 22. Pagefind 조각은 gzip이라 `out/` grep이 구조적으로 눈멀어 있다

`npx pagefind --site out` 이 `\037\213\b` 로 시작하는 `.pf_fragment` **242개**를 쓴다.
확실히 안에 있는 문자열도 `grep -a` 가 0을 낸다 — **대조군(`url`)도 0이므로**
그 0은 "없다"가 아니라 "읽을 수 없다"는 뜻이다.

`check-forbidden:built` 는 `out/blog` 를 훑으므로 이 파일들을 아예 보지 않는다:
배포 바이트에 본문 사본이 들어 있는데 어떤 검사기도 읽지 않는다.
손으로 한 번 확인했다 — 242개를 전부 펼쳐 3,992,070바이트, 스캔 결과 **그날은 유출 없음.**

**대응**

```
for f in out/pagefind/fragment/*.pf_fragment; do gzip -dc "$f"; done > /tmp/frag.txt
```

확실히 있는 대조 문자열을 항상 먼저 grep한다 — 압축된 입력에 대한 0은 증거가 아니다.
펼친 바이트도 순수 JSON이 아니다: 각 조각이 `pagefind_dcd` 접두로 시작해서
`JSON.parse` 가 `Unexpected token 'p'` 로 죽는다. 첫 `{` 부터 잘라 쓴다.

### 23. `/` 로 시작하는 지정자에는 `declare module` 이 적용될 수 없다

`import("/pagefind/pagefind.js")` 가 TS2307을 던진다.
`types/pagefind.d.ts` 에 `declare module "/pagefind/pagefind.js";` 를 넣어도 아무것도 달라지지 않는다.

문제는 그다음이다. `tsc --noEmit --listFiles | grep types/pagefind` 가
**그 d.ts가 프로그램에 포함되어 있음을 확인해 준다** — "선언은 로드됐으니 문제는 다른 데 있다"로 읽힌다.
아니다. TypeScript는 `/` 접두 지정자를 모듈 이름이 아니라 **루트 경로**로 해석하므로
어떤 앰비언트 선언도 맞을 수 없다. 이 확인 출력이 비용을 키운다 — `include` 패턴을 뒤지게 만든다. (T5)

**대응** — `tsconfig` 추적을 멈춘다. 번들러도 체커도 파싱할 수 없는 형태를 쓴다.

```js
new Function('return import("/path.js")')()
```

가정하지 말고 실제 브라우저에서 확인한다 — 여기서는 콘솔 에러 0에 결과 45건으로 실측됐다.
`unsafe-eval` 이 필요한데 GitHub Pages는 제한하지 않는다 (더 엄격한 호스트라면 문제가 된다).

### 24. 모르는 `--reporter` 는 테스트 하나 돌기 전에 vitest를 죽인다

`--reporter=basic` 은 vitest 4에 존재하지 않는다. **커스텀 리포터 모듈**로 취급되어
해석에 실패하고, 아무것도 실행하지 않은 채 1로 종료한다.

그 출력에서 `Tests  N failed` 를 파싱하던 뮤테이션 테스트 하네스가
**뮤턴트 14개 중 14개를 "생존"으로 채점**했다. 완벽하고 그럴듯한 거짓 보고였고,
앞선 리뷰어의 발견과 일치해서 더 설득력 있어 보였다. (T8 리뷰 수정 검증 중 발생)

**대응** — 카운트가 없다고 "실패 없음"을 추론하지 마라.
파싱하기 전에 실행이 **시작됐는지**(출력에 `Test Files`) 확인한다.
반드시 잡히는 것을 아는 **대조 뮤턴트**를 항상 포함시킨다 —
대조가 죽지 않으면 코드가 아니라 하네스가 고장난 것이다.
여기서 동작이 확인된 것은 `--reporter=verbose` 다.

### 25. 테스트의 `console.log` 가 파이프 아래에서 사라진다

TTY 실행에서는 찍히는 줄이 `npm test | grep 노드` 에서 0이 된다.

### 26. 코드 펜스 제거는 링크 쪽에는 맞고 헤딩 쪽에는 틀리다

`lib/atlas/links.ts` 의 `proseOnly` 는 펜스·인라인 코드·HTML 주석을 지운다.
산문 속 **예시** 링크가 진짜 엣지가 되지 않게 하고, 슬래시·앵커 검사기가
그것을 고칠 수 없는 위반으로 잡지 않게 하기 위해서다.

이것을 **대상** 쪽에도 적용했더니 앵커 2개가 깨졌다.

**대응** — 링크를 **뽑아내는** 곳에서만 전처리하고, 헤딩을 **색인하는** 곳에서는 하지 않는다.
이 변환은 대칭이 아니다 — **"일관되게 어디에나 적용"이 여기서는 결함 그 자체다.**

### 28. 생 NUL 바이트가 ripgrep으로 하여금 파일 전체를 건너뛰게 만든다

`tests/atlas/build.test.ts` 가 오프셋 11273/11283에 진짜 NUL 2개를 갖고 있었다 —
이스케이프로 의도한 템플릿 리터럴 구분자가 제어문자 자체로 들어갔다.

리포 전체 `Grep` 으로 `정준|결정론` 을 찾으니 23개 파일이 나왔고 **이 파일만 아무 표시 없이 빠졌다.**
UTF-8로 읽으니 정준 ×2, 결정론 ×1, `sort` ×3이 들어 있었다.
「이 파일에 그것이 없다」와 「이 파일은 스캔된 적이 없다」가 **같은 침묵**이라,
"정준 순서 테스트가 없다"는 거짓 발견이 나올 뻔했다.

**기전 (재현으로 확인)** — 도구 인자가 JSON으로 도착한다. 그래서 `\uXXXX` 는
파일에 닿기 전에 그 코드포인트로 파싱되지만, 8진 `\0` 형태는 유효한 JSON 이스케이프가 아니라서
텍스트로 살아남는다. **같은 파일의 한쪽만 오염된 이유가 이것이다.**
한 세션에 **세 번** 당했고, 세 번째는 Bash 도구가 제어문자가 든 명령을 거부해서 겨우 드러났다.

**대응** — 그런 시퀀스를 문자 그대로 두려면 백슬래시를 겹치거나
`String.fromCharCode(92) + "u0000"` 으로 만든다. 이스케이프가 든 파일을 쓴 뒤에는 NUL을 센다.

```
node -e "const d=require('fs').readFileSync(F); console.log(d.filter(b=>b===0).length)"
```

파일이 실제로 읽혔음을 증명하지 않은 채, 리포 전체 grep의 결과로 "없다"를 결론짓지 마라.

### 29. 부정 단언은 검사기가 동작해도 픽스처가 후보가 아니어도 초록이다

`expect(x).not.toContain(y)` 는 「면제가 동작한다」와 「이 픽스처는 후보였던 적이 없다」를
구분하지 못한다.

**실측** — 픽스처가 `graph.nodes[0]` (오늘의 정렬 순서 덕분에 우연히 artifact인 것)이던 자체 검사가,
첫 노드를 다른 타입으로 바꾸는 뮤테이션 아래에서도 **초록**을 유지했다.
반면 양성 형제 단언은 빨강이 됐다.
스위트는 한 번도 실행한 적 없는 면제 경로를 완전히 커버했다고 보고한다.

**대응** — 모든 부정 단언에 **차등 대조군**을 짝지운다.
면제 조건을 적용하기 **전에** 그것이 잡히는지 단언하고, 적용한 뒤에 잡히지 않는지 단언한다.
픽스처는 인덱스가 아니라 술어로 고른다: `filter(n => n.type === "artifact")[0]`.

### 30. 살아남은 뮤턴트는 뮤테이션이 아무것도 안 했다는 뜻일 수 있다

"생존"은 서로 다른 두 상태를 덮는다.

| 상태 | 뜻 | 읽히는 방식 |
| --- | --- | --- |
| 테스트가 닿지 못하는 분기 | 테스트가 약하다 | 맞다 |
| 어떤 출력도 바꿀 수 없는 변경 | 상수가 무력하다 | **틀리게 읽힌다** |

여기서 두 번 측정됐다.

- `CLUSTER_R_MAX 14 -> 30` — 계산된 클러스터 반경(12.90)이 상한에 닿은 적이 없어서 생존했다.
  **그 상수는 무력했다.**
- `lib/atlas/layout.ts` 의 `clamp` — 오늘 순수 항등(`v => v`)으로 생존한다.
  `npx vitest run tests/atlas` 는 여전히 통과를 보고하는데,
  `clusterCap` 의 viewBox 항이 이미 모든 좌표를 범위 안에 붙들고 있기 때문이다.

첫 경우는 "이 테스트가 약하다"로 읽혀서 **멀쩡한 테스트를 다시 쓰게 만든다.**

**대응** — "생존"을 믿기 전에 그 뮤턴트가 **출력을 바꾸는지** 증명한다 (양쪽 버전의 값을 찍어 본다).
한계처럼 읽히는 상수가 아니라 실제로 **구속하는** 상수를 바꾼다.
정말 무력한 분기를 남겨 두는 것은 괜찮지만 주석으로 말한다 —
"여기서 항등은 빨강이 되지 않으며, 그 이유는".

### 31. `getByRole` 개수는 Playwright 자신의 계산이지 접근성 트리가 아니다

Playwright는 `node_modules/playwright-core/lib/coreBundle.js` 안에
태그→role 표(`inputTypeToRole`)를 갖고 있다 — `injectedScript` 가 들어 있는 바로 그 번들(참조 50회).
그래서 role은 주입된 JS에서 DOM으로부터 유도된다.

따라서 `getByRole` 개수와 실제 브라우저 측정(탭 순서, 포커스 이동)이
**한 번의 도구 호출에서 똑같이 권위 있어 보이는데**, 엔진 자신의 답인 것은 두 번째뿐이다.

실제 사례로, 여기 코드 주석이 `getByRole("button")` 5 대 2 결과에 "Chromium 실측"이라고 적었고
리뷰어가 둘을 갈라내야 했다.

**대응** — 각 수치 뒤의 엔진을 밝힌다.
`getByRole` 은 스크린 리더가 노출하는 것의 강력한 근사이지만 **플랫폼 a11y 트리는 아니다** —
그 위에 실측이라고 쓰지 마라. [27번](#t27)과 같은 부류다.

### 32. 이 리포의 vite 는 oxc 라 `esbuild.*` 설정 키가 조용히 무시된다

**증상.** vitest 테스트에서 페이지를 import 하면 파싱이 죽는다.

```
import { getStaticProps } from "@/pages/atlas/[...id]"
→ Failed to parse source for import analysis … contains invalid JS syntax
```

**함정.** 원인은 대괄호 경로가 아니라 `tsconfig.json` 의 `jsx: "preserve"` 다 — 변환기가 JSX 를 그대로 두고
vite 의 import-analysis 가 그걸 JS 로 읽으려다 죽는다. 그런데 상식적인 처방인 `esbuild: { jsx: "automatic" }` 을
넣어도 **오류 문구가 한 글자도 바뀌지 않는다.** 이 리포의 vite 는 8.2.1(rolldown/oxc)이라 esbuild 를 쓰지 않고,
모르는 최상위 키를 경고 없이 버리기 때문이다.

바뀌지 않은 오류는 「설정이 안 먹었다」가 아니라 **「원인이 딴 데 있다」로 읽힌다.** 그래서 `include` 패턴과
alias 와 대괄호 파일명을 차례로 의심하게 된다 — 정작 방금 쓴 처방이 맞았는데 키 이름만 틀렸다.

**대응.** `oxc: { jsx: { runtime: "automatic" } }`. `vitest.config.ts` 에 이유와 함께 들어가 있다(`d217827`).
일반화하면: **설정을 바꿨는데 오류가 한 글자도 안 바뀌면 먼저 그 키가 읽히는지를 의심한다.**
빌드 도구를 갈아끼운 리포(vite 8 = rolldown/oxc, `esbuild` 아님)에서 특히 그렇다.

node -e "require('fs').writeFileSync('/tmp/probe.txt','x')"   # → C:\tmp\probe.txt 에 쓴다

### 34. 검사기의 빨강을 자기 스크립트로 진단하면 참인 관찰에서 틀린 인과가 나온다

셋 중 제일 값한다. 두 에이전트가 연달아 오진했고 **둘 다 관찰은 참이었다.**

**출발점.** `npm run build && npm run check-baseline` → exit 1 · 13건.

| | 진단 | 관찰 | 인과 |
| --- | --- | --- | --- |
| 오진 ① (리뷰어) | 「T11 의 `lg:grid-cols-[1fr_20rem]` 이 CSS 번들을 바꿨다」 | **참** — 번들에 그 클래스가 실제로 있다 | 틀림 |
| 오진 ② (검증 에이전트) | 「`buildId` 가 원인」 | **참** — 자기 비교 스크립트에서 남은 3곳이 전부 buildId 였다 | 틀림 |
| 실제 | CSS·JS **번들 파일명 해시** | | |

**함정.** `scripts/check-baseline.mjs` 의 `hashOf` 는 **buildId 를 이미 정규화하고 있었다.**
검증 에이전트의 비교 스크립트에는 그 정규화가 없었고, 자기 스크립트에서 본 차이를 검사기의 동작으로 일반화했다.
그대로 갔으면 **이미 있는 정규화를 한 번 더 넣고, 게이트는 여전히 빨간 채로 「고쳤다」고 보고**하게 된다.

번들 파일명이 진짜 원인인 이유는 공유 번들이기 때문이다 — 다른 페이지가 클래스를 하나 더 써도 파일명이 바뀌어
감시 대상이 전부 빨개진다. 그래서 새 화면을 만들 때마다 이 게이트가 통째로 빨갛고, 「원래 빨간 것」으로 학습된다.

**교정 절차.**

1. 자기 스크립트로 진단하기 **전에** `hashOf` 를 읽어 검사기가 **이미 정규화하는 축**을 확인한다
2. 정규화를 추가했으면 `--update` 로 기준선을 다시 만든다
3. 🔴 **반드시 대조군을 잰다.** 정규화 + `--update` 조합은 무엇을 하든 초록이 나온다 — 자기 자신과 비교하기 때문이다.
   `out/index.html` 의 `<body>` 에 속성 하나를 넣고 `check-baseline` 이 **exit 1 · 1건**인지 확인한다.
   실측: 번들만 바뀜 → exit 0, 마크업 한 글자 → exit 1. **이 둘이 갈려야 「고쳤다」이고, 안 갈리면 「검사를 껐다」다.**

**대응.** 에이전트 보고를 액면으로 받지 말고 검사기 소스를 직접 읽는다.
[24번](#t24)·[30번](#t30)과 같은 부류이되 한 겹 더 있다 — 저기서는 계측기가 안 돌았고, **여기서는 계측기가 돌았는데
다른 계측기였다.** 참인 관찰이 붙어 오므로 반증이 훨씬 어렵다.

*(다른 세션의 실측. 그 세션이 `hashOf` 소스를 직접 읽어 잡았다.)*

### 35. Git Bash 가 명령 인자 안의 `/atlas/` 를 윈도 경로로 바꾼다

**증상.** 뮤테이션 테스트에서 `url.includes("/atlas/")` 를 다른 문자열로 바꿔 넣었더니
**테스트가 빨개졌다.** 「뮤턴트 사멸 — 검사가 살아 있다」로 읽었다. 그런데 실제로 적용된 것은
그 문자열이 아니었다.

**재현 (2026-08-27 실측).**

```
$ node -e 'console.log(process.argv[1])' '/atlas/'
C:/Program Files/Git/atlas/          ← 홑따옴표로 감싸도 바뀐다
$ node -e 'console.log(process.argv[1])' '//atlas/'
//atlas/                             ← 앞에 / 를 하나 더 붙이면 안 바뀐다
$ MSYS_NO_PATHCONV=1 node -e 'console.log(process.argv[1])' '/atlas/'
/atlas/                              ← 환경변수로 꺼도 된다
```

**함정.** MSYS2 의 경로 변환은 **셸 인용을 지나서** 동작한다. `/` 로 시작하는 인자를
유닉스 경로로 보고 `C:/Program Files/Git/…` 로 바꾼다. 이 리포의 라우트는 전부
`/atlas/`·`/blog/`·`/en/` 꼴이라 **인자로 넘기는 순간 전부 표적이다.**

가장 나쁜 결과는 침묵이 아니라 **거짓 빨강**이다. 뮤테이션 테스트에서
「죽었다」와 **「엉뚱한 걸 죽였다」가 같은 빨강**이라, 뮤턴트가 실제로는 주입되지 않았는데
계수기가 살아 있다는 증거로 기록된다. [30번](#t30)의 거울상이다 — 저기서는 생존이 거짓이었고
여기서는 사멸이 거짓이다.

**대응.**

1. **치환 문자열을 인자로 넘기지 말고 스크립트 파일에 넣는다**(`Write` 로 쓰고 `node file.mjs`)
2. 넘겨야 한다면 `MSYS_NO_PATHCONV=1` 또는 `//atlas/`
3. 🔴 **치환 결과 줄을 `grep` 으로 눈으로 본다.** 뮤턴트를 주입한 뒤 그 줄이 의도한 모습인지
   확인하기 전에는 빨강도 초록도 증거가 아니다

*(2026-08-27 실측. 위 세 줄은 이 문서를 쓰면서 다시 실행한 것이다.)*

### 36. `\b` 를 문자열로 옮기려다 0x08 바이트가 파일에 박힌다

**증상.** 단어 경계 정규식 `/\bword\b/` 를 셸 경유로 파일에 쓴 뒤 실행하면 매칭이 안 된다.
`cat` 으로 보면 멀쩡해 보인다 — 0x08(백스페이스)은 터미널에서 **커서를 뒤로 움직일 뿐 보이지 않는다.**

**재현 (2026-08-27 실측). 범인은 히어독이 아니다.**

| 경로 | `\b` 가 도착하는 모습 |
| --- | --- |
| `cat > f <<'EOF'` (인용 히어독) | `\` `b` — **온전하다** |
| `cat > f <<EOF` (비인용 히어독) | `\` `b` — **온전하다** |
| `echo -e "a\bb"` | **0x08** |
| `printf 'x\by\n'` | **0x08** |

비인용 히어독이 먹는 것은 `\b` 가 아니라 **백슬래시 겹**이다 — 같은 실측에서
`"\\\\d"` 로 쓴 것이 파일에는 `"\d"` 로 도착했다(네 겹 → 한 겹). [8번](#t8)이 그것이다.

**함정.** 「히어독이 백슬래시를 먹는다」는 기억이 **`\b` 까지 히어독 탓으로 돌리게 만든다.**
그러면 히어독을 피하고 `printf` 로 우회하는데, 바로 그 `printf` 가 0x08 을 만든다.
**틀린 원인을 고치면 증상이 나빠진다.**

**대응.** `\` 가 들어가는 내용은 셸을 통과시키지 말고 **`Write`/`Edit` 로 파일에 직접 쓴다.**
셸을 써야 하면 인용 히어독(`<<'EOF'`)을 쓰고 `echo -e`·`printf` 의 포맷 문자열에는 넣지 않는다.
검증은 눈이 아니라 `od -c`(또는 `grep -P '\x08'`)다 — **`cat` 은 0x08 을 보여 주지 않는다.**

*(2026-08-27 실측. 위 표 네 줄을 직접 실행해 만든 것이다.)*

### 37. 뮤턴트 원복이 파일을 LF 에서 CRLF 로 바꿔 놓는다

**증상.** 뮤테이션 테스트를 마치고 `git checkout -- <file>` 로 원복했는데,
그 뒤의 `Edit` 이 **앵커를 못 찾거나 엉뚱한 곳에 붙는다.** `git diff` 는 깨끗하다.

**재현 (2026-08-27 실측, 빈 리포).**

```
$ git config core.autocrlf     → true      (.gitattributes 없음)
$ printf 'a\nb\nc\n' > f.txt && git add f.txt && git commit -m x
  커밋 전 CR=0
$ printf 'a\nb\nZ\n' > f.txt   # 뮤턴트 주입 (LF)
  뮤턴트 CR=0
$ git checkout -- f.txt        # 원복
  원복 후 CR=3                 ← LF 파일이 CRLF 로 돌아왔다
```

**함정.** `core.autocrlf=true` + `.gitattributes` 없음이 이 리포의 설정이다.
인덱스는 LF 로 저장하고 **체크아웃할 때 CRLF 로 편다.** 그래서 원복은 「원래대로」가 아니라
**「인덱스대로」**다 — 작업 트리에 LF 로 있던 파일은 CRLF 가 되어 돌아온다.

그리고 git 은 이 차이를 diff 로 보여 주지 않는다(같은 이유로 정규화하므로).
[9번](#t9)·[10번](#t10)·[14번](#t14)·[16번](#t16)과 같은 뿌리인데, **여기서는 내가 아무것도
안 썼는데 바뀐다** — 원복은 「되돌리는」 동작이라 의심의 대상이 되지 않는다.
2026-08-27 에 이렇게 3개 파일이 CRLF 가 됐고, 이후 `\n` 앵커 편집이 조용히 어긋났다.

**대응.**

1. 편집·주입 **전에** `tr -cd '\r' < f | wc -c` 로 CR 을 세고, **원복 후 다시 센다.** 두 값이 같아야 원복이다
2. 더 안전한 것은 git 을 거치지 않는 것이다 — `cp f f.bak` 으로 **바이트 백업**한 뒤 `cp f.bak f` 로 복원
3. `git checkout --` 로 원복했다면 그 다음 `Edit` 전에 CR 을 한 번 더 센다

*(2026-08-27 실측. 위 재현은 스크래치패드의 빈 리포에서 그대로 재현한 것이다.)*

### 38. `grep -c` 로 빌드 산출물의 요소를 세면 답이 항상 0 아니면 1이다

**증상.** `out/index.html` 의 `<h2>` 를 세려고 `grep -c '<h2' out/index.html` 을 돌리면 **1** 이 나온다.
실제 `<h2>` 는 4개다. 오류도 경고도 없다.

**재현 (2026-08-28 실측).**

```
$ grep -c '<h2' out/index.html          → 1     ← 틀림
$ grep -o '<h2' out/index.html | wc -l  → 4     ← 맞음
$ awk 'END{print NR}' out/index.html    → 1     ← 파일 전체가 한 줄이다
```

**함정.** `grep -c` 는 **매치한 줄 수**를 세지 세는 대상의 개수를 세지 않는다.
Next 의 정적 export 산출물은 **개행이 없는 단일 라인**이므로, 그 안에 요소가 몇 개 있든
답은 언제나 0(없음) 또는 1(있음)이다.

**이것이 위험한 진짜 이유는 1 이 그럴듯한 기대값이라는 데 있다.**
`id="main"` 1개 · 스킵 링크 1개 · `<h1>` 1개는 정답이 전부 1이라
**틀린 도구로 재도 맞는 답이 나온다.** 그래서 검사가 여러 번 통과한 뒤,
정답이 2 이상인 항목에서 처음 어긋난다 — 그때는 이미 그 도구를 신뢰하고 있다.

[16번](#t16)·[35번](#t35)과 뿌리가 다르다. 저것들은 「없다」와 「읽을 수 없었다」가
같은 출력으로 나오는 문제지만, **이것은 도구가 정직하게 답하는데 묻는 단위가 틀린 것**이다.
중복 컨트롤(같은 접근명 버튼이 둘)을 찾는 검사가 정확히 이 단위로 실패한다 —
1 이 나와서 「하나뿐」이라고 읽지만 실제로는 「그 줄에 있다」는 뜻일 뿐이다.

**대응.**

1. 산출물의 **개수**를 셀 때는 `grep -c` 를 쓰지 않는다. `grep -o <패턴> <파일> | wc -l`
2. 세기 전에 `awk 'END{print NR}' <파일>` 로 **줄 수를 먼저 본다.** 1 이면 `-c` 는 무의미하다
3. 정답이 2 이상인 마커를 **대조군으로 하나 끼워 넣는다.** 전부 정답이 1인 마커만 재면
   도구가 틀렸다는 것이 드러나지 않는다
4. `</head>` 이후만 재는 것과는 **다른 문제다.** 그쪽은 `__NEXT_DATA__` 중복을 배제하는 것이고
   이쪽은 단위 자체가 틀린 것이라, 둘 다 해야 한다

*(2026-08-28 실측. T10 검증에서 검증자가 발견해 재계수했다. 경위는
[`reports/2026-08-28-t10-main-sections.md`](superpowers/reports/2026-08-28-t10-main-sections.md) 의 Ruling R40.)*

### 39. `$TEMP` 를 POSIX 도구의 경로로 넘기면 「디렉터리가 없다」는 거짓말이 돌아온다

**증상.** 이전 커밋 상태를 재려고 `git archive <sha> content/blog | tar -x -C "$TEMP/before"` 를
돌리면 이렇게 죽는다.

```
tar: C\:\\Users\aeby\\AppData\\Local\\Temp/before: Cannot open: No such file or directory
tar: Error is not recoverable: exiting now
```

**함정.** 같은 명령의 바로 앞 `mkdir -p "$TEMP/before"` 는 **성공했다.** 디렉터리는 존재한다.
`$TEMP` 가 Windows 형식(`C:\Users\…`)이라 tar 가 백슬래시를 이스케이프 문자로 읽고,
경로가 뭉개진 채 열리지 않는 것이다. 메시지는 「없다」고 말하지만 실제 원인은 「경로가 틀렸다」다.

**이것이 위험한 이유는 진단이 엉뚱한 데로 간다는 데 있다.** 메시지를 곧이곧대로 읽으면
`mkdir` 이 실패했다고 보고 권한이나 디스크를 확인하게 되는데, 그쪽에는 아무 문제가 없다.

**대응.**

1. POSIX 도구(tar·rsync 등)에 넘길 임시 경로는 **`/tmp/<이름>` 을 직접 쓴다.** `$TEMP` 를 쓰지 않는다
2. `Cannot open: No such file or directory` 를 보면 **경로를 `echo` 로 먼저 찍어라.**
   백슬래시가 보이면 원인은 존재 여부가 아니다
3. [33번](#t33)과 뿌리가 같다 — 두 경로 세계가 한 명령 안에 섞이는 자리다

*(2026-08-29 실측. 알림센터 배치의 카테고리 링크 회고에서 당했다.)*

### 40. `python - <<'PY'` 의 한글 stdout 이 깨져도 파일 쓰기는 정상이다

**증상.** 문자열 치환 스크립트가 마지막에 `print('4건 교체')` 를 찍는데 콘솔에는
`4�� ��ü` 가 나온다.

**함정.** 깨진 것은 **stdout 인코딩뿐이고 파일은 정상으로 쓰였다.** 스크립트 안에서
`io.open(p, 'w', encoding='utf-8')` 로 쓴 내용은 온전하다. 그런데 출력이 깨져 있으면
「스크립트가 실패했다」로 읽고 되돌리거나 다시 돌리기 쉽다 —
**같은 치환을 두 번 돌리면 `assert a in s` 가 이번엔 걸려서 진짜로 실패한다.**

**대응.**

1. 출력이 깨져도 **실패로 읽지 마라.** 종료 코드를 보고, 결과는 파일을 다시 재서 판정한다
2. 확인은 `grep -c '<바뀐 문자열>' <파일>` 로 한다. 콘솔 메시지는 근거가 아니다
3. 굳이 찍어야 하면 **ASCII 로 찍어라** (`print('replaced 4')`)

*(2026-08-29 실측. 편5 원본 겹침 4건을 고치면서 당했다.)*

### 41. `io.open(p, "w")` 가 파일을 CRLF 로 바꾸고, 원본 대조가 거짓 0 을 낸다

**증상.** 축자 겹침 6곳을 파이썬 치환으로 고친 뒤 `source-overlap` 을 돌렸더니 세 원본
모두에서 **20자 0건**이 나왔다. 임계값을 **16자로 낮춰도 0건**이었다.

```
고치기 전   ① 11건 · ② 5건
CRLF 상태   ① 0건  · ② 0건      ← 거짓
CR 제거 후  ① 6건  · ② 3건      ← 참
```

**함정.** 파이썬은 텍스트 모드 쓰기에서 `\n` 을 플랫폼 개행(윈도에서는 `\r\n`)으로 **번역
한다.** `encoding="utf-8"` 만 주고 `newline` 을 비워 두면 파일 전체가 CRLF 가 되며, 실측으로
CR 이 **238개** 박혔다. `source-overlap` 은 빈 줄로 문단을 가르는데 `\r\n\r\n` 이 그 분할을
깨뜨려 **대조할 문단 자체를 잃는다.** 그런데 출력은 「0건」이라 **성공과 구별되지 않는다.**

37번(뮤턴트 원복이 LF 를 CRLF 로 바꾼다)과 원인이 다르다 — 그쪽은 git 체크아웃이고
이쪽은 파이썬 쓰기다. **증상이 같고 경로가 둘이라는 것이 요점이다.**

**왜 안 잡히나.** 여섯 곳을 고쳤으니 건수가 주는 것은 당연했고, 0 이 「다 고쳐졌다」로
읽혔다. 이상한 것은 **임계값을 낮춰도 0** 이라는 점 하나뿐이었다.

**대응.**

1. 발행본을 스크립트로 고쳤으면 검사기보다 **CR 계수를 먼저** 돌린다 —
   `tr -cd '\r' < <파일> | wc -c`. `grep` 은 CR 을 탐지하지 못한다(9번)
2. **대조군을 같이 센다.** 같은 배치의 앞 편이 CR 0 이면 이 파일만 오염된 것이다
3. 파이썬을 쓸 거면 **읽기·쓰기 양쪽에 `newline=""`** 를 준다
4. 되도록 `Edit` 도구로 고친다 — 개행을 건드리지 않는다
5. 🔴 **줄어든 0 을 통과로 세지 마라.** 「고쳤으니 줄었다」와 「검사기가 대상을 잃었다」는
   출력이 같다. 임계값을 낮췄는데도 0 이면 검사기 쪽을 의심한다

*(2026-09-02 실측. B 편1 원본 겹침을 고치면서 당했다. 설계서 §10-10-c 에 같은 기록이 있다.)*
